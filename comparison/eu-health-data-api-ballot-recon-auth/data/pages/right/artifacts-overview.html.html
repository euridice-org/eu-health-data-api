ActorDefinitions

NameTitleDescription
AuthenticationServiceEuApi

Authentication Service

The Authentication Service authenticates an end user, directly or through a Wallet or upstream identity provider, and supplies an authentication result trusted by the Health Data API Authorization Server. It does not grant API access or issue API access tokens in this role. This IG-defined role is not a formal IHE IUA or SMART actor. It MAY be grouped with the Health Data API Authorization Server in one implementation; the interface between separate implementations is deployment-defined, not an interoperable transaction specified by this IG. No ID token or token exchange is required by the actor split. See authentication and authorization groupings and Authorization.

DocumentAccessProviderEuApi

EEHRxF Document Access Provider

The Document Access Provider actor provides access to EEHRxF FHIR Documents by receiving documents from Document Publishers and serving them to Document Consumers. This composite actor groups MHD Document Recipient, MHD Document Responder, PDQm Patient Demographics Supplier, and the applicable IUA Resource Server or SMART FHIR Resource Server role. An Authorization Server is independent; it may be co-located only as an optional deployment. See Authorization for the selected role.

See Document Access Provider CapabilityStatement for technical requirements.

DocumentConsumerEuApi

EEHRxF Document Consumer

The Document Consumer actor consumes EEHRxF FHIR Documents by querying a Document Access Provider. This composite actor groups MHD Document Consumer, PDQm Patient Demographics Consumer, and the IUA Authorization Client, SMART App, or SMART Backend Service role selected by the environment and use case. The Authorization Server is a separate participant. See Authorization for the selected role.

See Document Consumer CapabilityStatement for technical requirements.

DocumentPublisherAccessProviderEuApi

EEHRxF Grouped Document Publisher/Access Provider

The grouped Document Publisher/Access Provider actor represents a deployment where document production and access provision are co-located in the same system. In this configuration, document submission (ITI-105) is internal and only document query/retrieval (ITI-67, ITI-68) is exposed externally. The external protected endpoint groups with the applicable IUA Resource Server or SMART FHIR Resource Server role. Internal publication does not create another externally advertised authorization role. An Authorization Server remains a separate participant and may be co-located only as an optional deployment. See Authorization for the selected role.

This is common for hospital EHR systems that produce and serve their own documents.

See Grouped Document Publisher/Access Provider CapabilityStatement for technical requirements.

DocumentPublisherEuApi

EEHRxF Document Publisher

The Document Publisher actor produces EEHRxF FHIR Documents and publishes them to a Document Access Provider. This composite actor groups MHD Document Source, PDQm Patient Demographics Consumer, and the IUA Authorization Client or SMART Backend Service role selected by the environment and use case. The Authorization Server is a separate participant. See Authorization for the selected protocol and flow.

See Document Publisher CapabilityStatement for technical requirements.

EuAuthorizationClientEuApi

Health Data API Authorization Client

The Health Data API Authorization Client obtains an access token from the selected Authorization Server and presents it to a protected API. Client authentication, grants, scopes, discovery, and launch context depend on the selected environment and protocol; public SMART interactive clients do not authenticate at the token endpoint. This generic role does not by itself claim IHE IUA or SMART conformance. See the applicable IHE IUA Authorization Client, SMART App, or SMART Backend Service definition and the relevant Authorization requirements.

EuAuthorizationResourceServerEuApi

Health Data API Resource Server

The Health Data API Resource Server hosts a protected API, validates or introspects access tokens as applicable, and enforces granted authorization and local policy. It does not issue access tokens or validate client assertions for an independent Authorization Server. This generic role does not by itself claim IHE IUA or SMART conformance. See the applicable IHE IUA Resource Server or SMART FHIR Resource Server definition and the relevant Authorization requirements.

EuAuthorizationServerEuApi

Health Data API Authorization Server

The Health Data API Authorization Server issues access tokens after applying the authentication and authorization requirements of the selected environment and protocol. When user authentication is required, it relies on an acceptable result from the Authentication Service, with which it MAY be grouped. Authentication alone does not establish API access entitlement. Client assertion validation applies only when the selected flow uses asymmetric client authentication. The Authorization Server remains responsibility-distinct from a Resource Server, including when the two are co-located. This generic role does not by itself claim IHE IUA or SMART conformance. The Health Data API qualifier identifies this IG's role, not a central EU-operated service. See the applicable IHE IUA Authorization Server or SMART Authorization Server definition and the relevant Authorization requirements.

IuaAuthorizationClientEuApi

IHE IUA Authorization Client

The IHE IUA Authorization Client authenticates to the Authorization Server, requests least-privilege scopes, and presents the resulting bearer token to the Resource Server. It implements the applicable IUA transactions. See the IHE IUA Authorization Client and Authorization.

IuaAuthorizationServerEuApi

IHE IUA Authorization Server

The independent IHE IUA Authorization Server authenticates clients, validates client assertions when selected, applies issuance policy, prevents replay, and issues tokens. Where user authentication is required, it may use the IG-defined Authentication Service; this does not remove any applicable IUA Authorization Server conformance obligation. It does not provide protected-resource enforcement. See the IHE IUA Authorization Server and Authorization. IUA requires this role to be grouped with a CT Time Client; see required actor groupings and the shared Time Synchronization deployment guidance.

IuaResourceServerEuApi

IHE IUA Resource Server

The IHE IUA Resource Server validates or introspects access tokens and enforces granted authorization and local policy for protected resources. It does not validate client assertions for an independent Authorization Server. See the IHE IUA Resource Server and Authorization. IUA requires this role to be grouped with a CT Time Client; see required actor groupings and the shared Time Synchronization deployment guidance.

ResourceAccessProviderEuApi

EEHRxF Resource Access Provider

The Resource Access Provider actor provides access to FHIR resources following IPA patterns. This enables direct resource access complementing document-based exchange. This composite actor groups IPA Server, PDQm Patient Demographics Supplier, and the applicable IUA Resource Server or SMART FHIR Resource Server role. An Authorization Server is independent; it may be co-located only as an optional deployment. See Authorization for the selected role.

See Resource Access Provider CapabilityStatement for technical requirements.

ResourceConsumerEuApi

EEHRxF Resource Consumer

The Resource Consumer actor queries for clinical data resources from a Resource Access Provider following IPA patterns. This composite actor groups IPA Client, PDQm Patient Demographics Consumer, and the IUA Authorization Client or SMART App or SMART Backend Service role selected by the environment and use case. The Authorization Server is a separate participant. See Authorization for the selected role.

See Resource Consumer CapabilityStatement for technical requirements.

SmartAppEuApi

SMART App

The SMART App is an interactive client using authorization code and PKCE in standalone or EHR-launch mode. See SMART App Launch and Authorization.

SmartAuthorizationServerEuApi

SMART Authorization Server

The SMART Authorization Server authenticates clients as applicable, authorizes requests, and issues tokens. It remains a distinct participant from the protected FHIR Resource Server. For interactive flows it may rely on the IG-defined Authentication Service for user authentication without transferring its SMART conformance obligations. Backend Services does not require runtime end-user authentication. See SMART App Launch and Authorization. This IG recommends CT Time Client grouping for this server role in both interactive and Backend Services modes; see SMART Server Time Synchronization and the shared Time Synchronization deployment guidance.

SmartBackendServiceEuApi

SMART Backend Service

The SMART Backend Service is a pre-authorized confidential server-side client using client credentials, asymmetric client authentication, and applicable system scopes. See SMART Backend Services and Authorization.

SmartFhirResourceServerEuApi

SMART FHIR Resource Server

The SMART FHIR Resource Server hosts protected FHIR resources, validates access tokens, and enforces granted SMART scopes. See SMART App Launch and Authorization. This IG recommends CT Time Client grouping for this server role in both interactive and Backend Services modes; see SMART Server Time Synchronization and the shared Time Synchronization deployment guidance.

SmartLaunchingSystemEuApi

SMART Launching System

The SMART Launching System initiates an EHR launch and supplies the launch context for an interactive SMART App. See SMART App Launch and Authorization.

NameTitleDescription
Example - European Patient Summary DocumentReference

Example DocumentReference showing an EPS document with EEHRxF category coding.

This example demonstrates the recommended search strategy:

  • category = Patient-Summaries (EHDS priority category for coarse filtering)
  • type = 60591-5 (LOINC code for clinical precision)

Example query to find this document by priority category:

GET [base]/DocumentReference?patient=Patient/example-patient&category=https://euridice.ec.europa.eu/fhir/eehrxf/CodeSystem/document-priority-category-eu-api|Patient-Summaries

Example query to find this document by type:

GET [base]/DocumentReference?patient=Patient/example-patient&type=http://loinc.org|60591-5
